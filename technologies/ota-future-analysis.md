# OTA 的未来与 Agent 的机遇

> AI Agent 会不会让携程这样的 OTA 变得多余？—— 一次完整的推演

## 引言

在一次技术路径讨论中，我们聊到一个问题：**如果 AI Agent 能轻松获取所有酒店的信息，OTA（在线旅游平台）还有存在的意义吗？**

这个问题的答案，比"会消失"或"不会消失"要复杂得多。以下是我们完整的推演过程。

---

## OTA 到底在卖什么？

大多数人觉得 OTA 的功能是"帮你找到合适的酒店"。但拆开来看，OTA 实际上提供了 **5 层价值**：

| 层级 | 服务 | 能被 Agent 替代？ |
|------|------|:--------------:|
| ① 发现 | 搜酒店、比价格、看评价 | ✅ **完全可替代** |
| ② 信任 | 住客评价体系、评分、图片 | ✅ 部分可替代（链式验证而非中心化评分） |
| ③ 交易 | 支付、担保、取消政策执行 | ⚠️ 需要新的基础设施 |
| ④ 售后 | 纠纷仲裁、退款、客服 | ❌ 最难替代 |
| ⑤ 流量 | 把酒店推到用户面前 | ❌ 这是他们的核心壁垒 |

### 1. 发现层 — OTA 的死穴就在这里

如果所有酒店都以标准化的接口广播数据（价格、房态、设施、实时可用性），Agent 可以直接做智能匹配。用户不再需要打开携程网页、手动筛选几十家酒店——Agent 直接理解需求，给出最优推荐。

这意味着 OTA 作为"信息中间人"的价值归零。

### 2. 信任层 — 中心化评分 vs 链式验证

OTA 的评分体系有几十万条真实住客评价做锚定。如果所有酒店 self-broadcast，谁来防止酒店刷假数据？

这不是技术问题，是博弈问题。OTA 之所以有价值，部分是因为他们作为中立第三方，评价体系相对可信。

可能的替代方案：**区块链/去中心化身份验证**，让住客的真实入住记录可验证，构建不可篡改的信用体系。

### 3. 交易层 — 可以绕过，但不能没有

支付、担保、取消政策执行。这些功能不需要 OTA 来做——银行、支付平台、智能合约都可以承担。

### 4. 售后层 — OTA 最后的护城河

假设 Agent 帮你订了房，到了酒店发现没房了，或者房间跟描述不符。**谁负责？**

OTA 在这里实际上是一个**保险角色**——携程会赔你、帮你换房、扣酒店的钱。没有 OTA，这个纠纷链条回到酒店和客人之间，而小酒店的履约能力参差不齐。

这是最难替代的一层，因为它涉及的是**责任归属和信用背书**，不是信息处理。

### 5. 流量层 — 不可忽视的霸权

OTA 最大的筹码不是技术，是**流量**。携程每年花几十亿买搜索引擎关键词、投广告、做会员体系。酒店之所以忍受 OTA 的高佣金（15%-25%），不是因为 OTA 技术好，而是因为 OTA 能带来客源。

Agent 解决了"信息匹配"，但解决不了"没人知道你"的问题。

---

## 最可能发生的演变

不是一刀切的"OTA 消失"，而是**分层瓦解**：

```
现在：
  用户 → 携程 → 酒店

短期：
  用户 → Agent → 聚合搜索API（比价） → 携程 → 酒店

中期：
  用户 → Agent → 聚合搜索API（比价） → 酒店（直连）
                    ↑
              这里替代了 OTA 的发现层

远期：
  用户 → Agent → 酒店（自建 broadcast）
         ↑
   去中心化信用体系替代 OTA 的信任层
```

### 关键转折点

| 阶段 | 时间预估 | 标志事件 |
|------|---------|---------|
| 短期 | 1-2 年 | Agent 成为比价入口，但仍需 OTA 完成交易和售后 |
| 中期 | 3-5 年 | 中大型酒店开始自建直连接口，OTA 的发现层价值被压缩 |
| 远期 | 5-10 年 | 去中心化信用体系成熟，OTA 退化为"售后保险"角色或彻底转型 |

---

## 携程们不会坐以待毙

OTA 自己也在变化。他们正在做的防御动作：

1. **内容化** — 小红书式种草、短视频探店、直播带货，加固流量层
2. **会员体系** — 携程钻石会员、积分权益、机场贵宾厅，增加用户粘性
3. **供应链深挖** — 独家房源、打包套餐、企业客户协议价，让酒店不能轻易脱离
4. **AI 化** — 携程也在接入大模型，试图自己成为 Agent

因为他们自己也知道，"比价"这个功能的价值正在被 AI 消解。

## 对 Trinity 意味着什么

回到我们的核心问题：**如果酒店能自己 broadcast 数据，OTA 的价值在哪里？**

Trinity 现在做的事情，正是在走这条路：

```
Trinity PMS → 酒店数据 broadcast API → Agent → 用户
```

如果你能让连入 Trinity 的酒店以标准化接口 broadcast 数据——价格、房态、设施、实时可用性——你就不需要经过任何 OTA。Agent 可以直接查你体系内的酒店，用户直接预订。

### Trinity 的优势

- **供给侧直连** — PMS 本身就是酒店管理系统，数据天然存在
- **不需要说服酒店"接入平台"** — 酒店已经是 Trinity 的用户
- **Agent 友好** — 标准化 API 天然可为 Agent 消费

### 需要解决的问题

1. **发现问题** — 如何让用户（或用户的 Agent）知道你体系内的酒店？
   - 答案：开放搜索 API，让所有 Agent 都能查询
2. **信任问题** — 如何让住客相信你的数据是真实的？
   - 答案：构建可验证的入住记录链，或者引入第三方评价体系
3. **售后问题** — 交易出问题谁负责？
   - 答案：初期可能需要自建客服团队，或与保险平台合作

---

## 最终的判断

**你不需要打败携程，你只需要让携程变得多余。**

OTA 不会一夜消失，但它们的核心价值正在从"信息匹配"向"风险担保+流量分发"转移。对于 Trinity 来说，关键是抓住**发现层**的空缺——让 Agent 可以直接查询你的酒店数据，让用户不需要打开携程就能完成"发现→决策→预订"的完整链路。

这个窗口期大概还有 2-3 年。等到所有 OTA 都完成了 AI 化转型，窗口就关上了。
